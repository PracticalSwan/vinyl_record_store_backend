# Backend Risk Register

| ID | Risk | Impact | Mitigation | Status |
| --- | --- | --- | --- | --- |
| BR-001 | Credentials leak. | High | Keep Atlas credentials in ignored `.env.local`; scripts log only safe status and error names. | controlled |
| BR-002 | Private interaction data is exposed. | High | Accept only the versioned bounded schema, reject PII/unknown fields, return counts rather than rows, apply TTL retention, and remove owned events on account deletion. | controlled |
| BR-003 | API contract drifts. | High | Update both repos and validate builds together. | controlled |
| BR-004 | Demo output is presented as real personalization. | High | Explicit demo-profile/cold-start modes. | controlled |
| BR-005 | Fixed weights produce weak relevance. | Medium | Document weights and require offline baseline evaluation before quality claims. | open |
| BR-006 | Catalog metadata is incomplete, mismatched, or biased. | Medium | Use a controlled genre taxonomy, conservative artist/year rules, preserve raw operator provenance, sample every canonical genre, accept only strict unique MusicBrainz release-group matches, visually review the fixed legacy bundle, hash-verify both local-art sets, and retain placeholders. | controlled |
| BR-007 | One artist dominates a list. | Medium | Cap at two results per artist. | controlled |
| BR-008 | Implemented state APIs are mistaken for production commerce. | Medium | Document the local-UI migration boundary and absence of orders, payments, recovery, deployment hardening, and quality evidence. | controlled |
| BR-009 | CORS origin is misconfigured. | Medium | Configure `FRONTEND_ORIGIN` and verify live when environment permits. | open |
| BR-010 | Invalid input creates unsafe work. | High | Bound IDs, limits, pagination, prices, booleans, and user ID syntax. | controlled |
| BR-011 | Explicit MongoDB mode hides a database failure by serving seed data. | High | Never silently fall back; return `503 PERSISTENCE_UNAVAILABLE`. | controlled |
| BR-012 | Seed migration overwrites unrelated or ambiguous records. | High | Dry-run first, refuse identity/source conflicts, transact writes, and never delete records. | controlled |
| BR-013 | Framework transitive dependencies introduce security advisories. | High | Use Next.js 16.2.12, align `eslint-config-next`, and override to patched PostCSS 8.5.18 and Sharp 0.35.0; gate release on tests, lint, build, and a zero-finding npm audit. | controlled |
| BR-014 | A forged request mutates another account. | High | Derive ownership only from a revalidated signed session; reject client user IDs and require the exact configured origin. | controlled |
| BR-015 | Session or password material leaks. | High | Use scrypt, signed HttpOnly cookies, non-selecting password fields, generic failures, safe logs, ignored environment files, and no secret response fields. | controlled |
| BR-016 | A retry duplicates guest state or events. | High | Enforce unique event IDs and stable merge receipts/input hashes; test replay behavior and cart quantity caps. | controlled |
| BR-017 | Logged lists cannot join events or expose identity. | High | Generate request/list IDs server-side, derive authenticated ownership from the session, hide subjects, require complete event context, honor opt-out, and apply TTL. | controlled |
| BR-018 | External catalog or artwork services are unavailable, redirected, or rate-limited. | Medium | Use a meaningful User-Agent, no faster than one MusicBrainz request per second, bounded retries/timeouts, per-hop redirect allowlists, a resumable local cache, no broad scraping, placeholders instead of uncertain data, and verified committed fallbacks for all 116 legacy covers plus every accepted current-v3 decision and the pinned v2 rollback set. | controlled |
| BR-019 | Sparse interactions produce misleading quality claims. | High | Require 20 eligible subjects with 5 final positive products each; below that threshold emit aggregate completeness and an explicit non-conclusion only. | controlled |
| BR-020 | Planned personalization is presented as real measured quality. | High | Honesty wording is frozen; PERS-00/01/02 retain `content-demo-v1` and `insufficient-evidence`, and synthetic fixtures remain labelled demonstrations. | controlled |
| BR-021 | The arbitrary-user recommendation route leaks private profile data after personalization lands. | High | PERS-01 restricts the route to explicit demo/cold-start descriptors; non-`demo-user` ids never read profile data, and cross-user denial tests gate PERS-03. | controlled |
| BR-022 | Tracking opt-out accidentally disables direct account features or passive events still persist. | High | PERS-06 keeps rating/wishlist/cart/feedback on their functional APIs, suppresses only passive `/interactions` persistence/use under opt-out, and tests both boundaries. | controlled |
| BR-023 | Stored preferences remain inert or research-only null fields distort scoring. | Medium | Implemented PERS-04 uses only actual preference-schema fields, treats disliked genres as bounded soft penalties, ignores null commercial fields, and returns a directly bounded score; PERS-08 remains responsible for later component blending. | controlled |
| BR-024 | A single negative signal suppresses an entire genre. | Medium | Implemented PERS-05 performs exact-item suppression only; PERS-06 may use not-interested as bounded attribute evidence but never as an attribute exclusion. | controlled |
| BR-025 | Preference semantics in code do not match the UI. | Medium | Implemented PERS-04 treats favorite/disliked genres, artists, and formats as soft knowledge-based signals and has no silent hard-constraint relaxation path. | controlled |
| BR-026 | Popularity mixes dataset versions, leaks historical identity, or leaks held-out data into evaluation. | High | PERS-07 filters the production aggregate by the exact active dataset key, returns aggregates only, and keeps the offline popularity baseline train-only. | controlled |
| BR-027 | Hybrid double-counts content or silently changes weights/mode/reasons. | Medium | PERS-08 blends only when preference + behavior both exist, optionally adds popularity, keeps lower modes pure, uses versioned 0.45/0.35/0.20 assumptions, and performs no second min-max pass. | controlled |
| BR-028 | Personalization cleanup is incomplete or an in-flight recommendation recreates subject-linked analytics after account deletion. | High | Account deletion removes all owned state in one transaction; PERS-09 makes authenticated recommendation logging revalidate and write-fence the active customer in the same transaction as log creation, so deletion either removes the log afterward or wins before logging. Deterministic transaction, rollback, and deletion-race regressions cover the boundary. | controlled |
| BR-029 | Raw external data, reviewer identity, or unlicensed content is committed or exposed. | High | Pin manifest/hashes, ignore raw/staging, HMAC reviewer keys, exclude review text/Amazon images/profiles, commit only opaque product identities and aggregate evidence, document Cover Art Archive provenance/rights limits, and expose aggregate readiness only. | controlled |
| BR-030 | Dataset activation corrupts or strands the storefront. | High | Separate import from activation, verify exact counts/indexes, allow one transactional active pointer, preserve the 116 legacy records, and provide non-destructive rollback. | controlled |
| BR-031 | Missing source fields are presented as invented store facts. | High | Keep artist/price/currency/stock/condition/format nullable with field origins; render Unknown/Unavailable and block purchase when commercial state is unknown. | controlled |
| BR-032 | Historical Amazon subjects are confused with the three showcase customers or live evidence. | High | Store ratings in an isolated collection, never create `User` rows, verify the exact demo IDs after activation, and label readiness as historical data preparation rather than model quality. | controlled |
| BR-033 | Recommender enablement silently begins because historical data is ready. | High | PERS-09 closure keeps PERS-04 through PERS-08 explicitly default-off, preserves `content-demo-v1`, and makes no model/evaluation quality claim. | controlled |
| BR-034 | A repeated apply mutates or leaves stale rows under a sealed dataset key. | High | Each sealed release uses `$setOnInsert`, exact record digests, version-owned source/staging/config/identity/artwork checks, sealing, exact-set verification, and cleanup only for an unsealed inactive failed import. | controlled |
| BR-035 | Product IDs drift across v1, v2, and v3, breaking deep links or saved state. | High | Commit an opaque identity registry derived from v1, use fixed `record-<publicId>` slugs, verify every sealed release against the v1 mapping, refuse missing registry rows, preserve unavailable state without remapping, and verify the v2 rollback target independently while v3 is active. | controlled |
| BR-036 | The historical final test is reread, tuned against, or mistaken for all-subject evidence. | High | NEXT-03 creates an exclusive permanent attempt claim before the first test query, binds the full execution boundary, records no post-test tuning, and labels its 1,708-subject cohort as conditional on a relevant target. | controlled |
| BR-037 | A weak offline latent model is promoted because it appears more advanced. | High | Report the negative biased-MF result unchanged, keep it offline-academic-only, reject live integration, and retain source ranking defaults off. | controlled |
| BR-038 | Strong positive-rating skew is mistaken for balanced evidence. | High | Publish the unchanged 1-to-5 distribution and positive rate, state that no ratings were rebalanced and no negatives were fabricated, and require future experiments to account for the skew without changing source labels. | controlled |
| BR-039 | Repeated weak passive events overwhelm stronger durable customer intent. | Medium | PERS-06 gives durable state precedence and bounds passive evidence with day deduplication, recency bands, per-product caps, and absolute artist/genre/format caps. | controlled |
| BR-040 | The selected classroom flags are mistaken for committed defaults or measured live quality. | High | Keep source defaults unchanged, name Profile B as an environment-only functional demonstration, and link every startup path to the runbook and explicit claim boundary. | controlled |
| BR-041 | MongoDB becomes unavailable during the primary demo and seed fallback hides the failure. | High | Require the health preflight to report MongoDB mode, fail explicit MongoDB requests with `503 PERSISTENCE_UNAVAILABLE`, and use the documented seed path only as a visibly different emergency demonstration. | controlled |
